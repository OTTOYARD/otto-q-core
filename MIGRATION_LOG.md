# MIGRATION_LOG.md — the human record

One row per change to the OTTO-Q brain. Newest at the top.

This is the record a person reads. `supabase_migrations.schema_migrations` says
*that* something was applied; this file says **what it did and why**, in language
someone can act on six months from now at 2am.

**Every applied migration gets a row here.** Including hotfixes typed live during
a demo — those get their row the same day. See `scripts/APPLYING.md`.

**"Verified" is not "applied without error."** It is the query, count, or run
that proves the behaviour actually changed. If that column says "n/a", the change
is not finished.

## ⚠️ THREE THINGS 0006 LEAVES OPEN — read before the next run start

Found while verifying 0006, reported rather than quietly patched. None of these were introduced by
0006's own edits; two are pre-existing and one is a real limitation of 0006's new retention walk.

### 1. ⚠️ THE NEXT RUN START WILL, FOR THE FIRST TIME, ACTUALLY DELETE THE PRIOR RUN'S EVENTS

`ottoq_start_demo_run` calls `ottoq_purge_prior_runs`, and until 0006 that call **silently deleted
nothing from `ottoq_events`** — the append-only trigger refused it and the handler swallowed the
refusal. It is now armed and it works: measured `rows_purged: 6` on a bounded test. **So the
long-standing habit of "just start a run" now has a consequence it never had before.** As of this
writing that means the **9,561 events of run `83a12664`** (the post-recovery verification run) are
deleted the moment anyone starts a new run.

**Preserve anything you still want into a NON-`ottoq`-prefixed table first.** This is not a defect —
it is the fix working — but it is a sharp edge that did not exist yesterday.

### 2. THE NEW RETENTION WALK CAN STOP EARLY AND LEAVE GENUINELY OLD ROWS BEHIND

§7 replaced the quadratic `ctid` cursor with an ordered walk on `event_seq`, which is correct and is
a real improvement. But its early-exit —

```
IF v_n = 0 AND v_batch_ts >= v_cut THEN … EXIT; END IF;
```

— assumes **`event_seq` order is `occurred_at` order**. That assumption is already false in this
database, and it was measured, not theorised:

- **11 seq/time inversions** inside run `83a12664` alone (9,559 adjacent pairs compared).
- **Demonstrated end to end:** with a 30-day-old row present and the real 7-day policy, one call to
  `ottoq_retention_purge_worker(30, 2000, '7 days', …)` processed exactly **one** window
  (watermark advanced `8673216 → 8675216`), deleted **0**, and exited — while
  `count(*) WHERE occurred_at < cut` stayed at **1**. The armed worker reported success and deleted
  nothing, which is the *same shape* of failure 0006 set out to end, for a new reason.

**Why it matters beyond the test:** `occurred_at` is written from the **SIM clock**, and per the
arrival/tick doctrine a run starts at a **random time of day**. A run whose sim clock sits behind the
previous run's writes old-timestamped rows at high `event_seq`, and the walk exits before reaching
them. The ordinary case (old runs at low seq) works fine.

**Not fixed here — out of 0006's scope, and the fix is a judgement call:** either drop the early exit
and let `p_time_budget_s` bound the pass, or drive the walk from an index on `occurred_at` (which does
not exist — see the file's own §1 (3): the only `occurred_at` indexes are one partial and one BRIN).

### 3. THE PURGE LOOP TRIES TO DELETE FROM VIEWS, AND NOW SAYS SO OUT LOUD

`ottoq_purge_prior_runs` picks its targets from `information_schema.columns`, which lists **views** as
well as tables. Three of them have a `sim_run_id` column, so every purge has always issued a `DELETE`
against them and always failed:

`ottoq_active_sim_runs`, `ottoq_approach_band`, `ottoq_booking_why_v1` — all confirmed `relkind='v'`.

This is **pre-existing, not a 0006 regression**. What changed is that 0006 stopped swallowing the
failures, so they now surface as `"ok": false` with a named `failed_tables` array. **Read `ok: false`
here as "the honest reporting works", not as "the purge broke"** — the row counts confirm the real
tables were purged correctly. The one-line fix (restrict the loop to `information_schema.tables` /
`relkind='r'`) belongs in its own migration.

## How to add a row

Copy the row shape above. Fill in all six columns.

- **Date** — the day it was applied to the live database, not the day you wrote it.
- **File** — `db/migrations/NNNN_short_name.sql`.
- **What changed** — the objects touched and the behaviour that moved. Not "fix".
- **Why** — the symptom that started it. A number is worth ten adjectives.
- **Applied by** — a person or agent, and the path used (MCP `apply_migration`,
  Supabase CLI, or dashboard SQL editor). If it was the SQL editor, say so —
  that path writes no ledger row and the drift check cannot see it.
- **Verified** — the proof. Query, count, or run result.

Then re-run `scripts/check-drift.sql` and confirm **CLEAN**.
