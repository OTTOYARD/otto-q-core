# Lab engine fidelity — 2026-11-03

**What was measured.** The OTTO-Q engine database was rebuilt from this repository alone
(`db/baseline/` + `db/migrations/`, at `main` 4a71274) into a local PostgreSQL 17.11 (`ottoq_lab`, port
55433), and every routine, table, view, trigger and type in schemas `public`, `ottoq` and `twin` was
compared with production (`gxdrcyphqjzjsuhxuqtg`, PostgreSQL 17.6) through read-only `SELECT`s. No
simulation was run, nothing was written to production, and no function body or row was copied out of it
(the one exception, named below, is enum labels and two composite types the repository does not hold).

## The answer

**The repository cannot rebuild the engine today.** The copy matches production on **300 of 1,037
routines (28.9%)** and **177 of 453 tables (39.1%)**, and has **3 of production's 236 triggers**. Of the
718 post-baseline migrations it tried, **77 applied and 641 failed**. That is a finding about the
repository, not a failure of the build, and it has five causes, in the order the replay meets them:

1. **The baseline export is incomplete.** It has no triggers, no types, no sequences, no `ottoq`/`twin`
   schemas and no grants. Types and schemas were filled from production's catalog (`sql/20_repo_gaps.sql`)
   and sequences from the dump's own `nextval` defaults; triggers were not filled, so the 233 missing
   triggers (append-only guards, state-change probes, run-scope stamps) are the baseline's gap.
2. **The migration files are not the SQL that ran.** Production's ledger stores the exact text of each
   apply. Of the 586 repo files whose ledger row has that text, **101 match it** (once the version header
   is put back to `PENDING`, as the house rule writes the real version only after the apply) and **485 do
   not**: 473 are longer than what ran (median +4,031 characters), i.e. annotated or extended after the
   apply. A function created from such a file differs from production's, and the next file that pins the
   body's md5 refuses. The first lineage break is exactly this: `0012`'s file is 21,774 characters and its
   ledger statement 7,873; the metronome body in the file is 8,032 characters and the one in the statement
   that ran 6,398; so `0013`'s pin (`da1736f0…`) fails.
3. **84 post-baseline ledger rows have no file on `main`:** the 67 of 2026-08-10..16 that
   `db/migrations/UNFILED.md` enumerates (arm, tether, charge-target work), 14 split-apply parts of
   `0045`/`0050`/`0051`/`0052` (their parent files exist), 1 part of `0350` (`20260919185656`), and 2
   applied today from unmerged branches: `20261103041827` = `0792` (branches
   `claude/faulted-post-releases-its-car`, `claude/phase0-lab`, `claude/lab-post-cell-supervisor`) and
   `20261103155140` = `0793` (`claude/phase0-lab`).
4. **Migrations assert facts about production's rows.** 40 files stop on a guard that needs a depot, its
   stalls, rule rows, catalog rows, ledger or evidence rows (`0010`: "no depot has any stalls"; `0018`: "no
   Nashville depot"). An empty copy can never satisfy them, so their DDL never lands.
5. **Everything after cascades.** 333 files fail on a missing object, 76 on a missing prerequisite and
   184 on a body-lineage guard (md5 pin, pre-image, anchor count).

So the repository is the source of truth for **what was intended**, and production's ledger
(`supabase_migrations.schema_migrations.statements`) is the source of truth for **what ran**. A faithful
lab needs the second (or a schema-only export of production); see "What it would take".

## Fidelity

Classes. **Routines:** *identical* = same `prosrc` md5 and same header md5 (kind, language, volatility,
security definer, strict, set-returning, parallel, leakproof, cost, rows, full argument list with
defaults, result type, `SET` options); *code differs* = body md5 differs and so does the comment- and
whitespace-blind body md5; *comments only* = only the comment-blind md5 agrees; *header only* = body
equal, header not. Identity = schema + name + identity arguments. **Tables:** a column is name, type, not
null, default, identity, generated; *identical* = same columns in the same order; *order only* = same
set. **Views:** columns plus `pg_get_viewdef`. **Triggers:** `pg_get_triggerdef`. Extension-owned objects
are excluded on both sides; both sides ran with search_path `"$user", public, extensions`.

## What it would take

- **Replay what ran, not what was filed.** The ledger holds the applied text of 670 post-baseline rows
  (and of the 621 before them); replaying those statements in version order, with the repo files used
  only where a row's statements are NULL (46 rows, 2026-09-19..25), would remove causes 2 and 3. Reading
  that much SQL out of production is beyond this task's read-only budget and is a decision for Chase.
  A schema-only export of production (`pg_dump --schema-only` with a database credential) is the other
  route, and the simpler one.
- **Load reference data before the data-premise migrations,** or make those guards lab-aware. Reference
  data for the twin depot is listed below; copying it is a separate, approved step.
- **Re-export the baseline with triggers, types, sequences and grants,** or retire it in favour of either
  route above.
- Sibling repositories hold part of the unfiled window: `otto-q-workspace/supabase/migrations/` has 37
  files dated 2026-08-12..15 and `ottoyarddepot-sim/supabase/migrations/` 2, several under timestamps that
  differ from the ledger's. They were not used here.

## What could not be verified

- Whether the lab **behaves** like production: nothing was run, by instruction.
- ACLs, owners and comments of objects that compare identical: not compared.
- Constraints, indexes, policies and row-security flags: compared by count, not object by object.
- The position of the 86 files with no ledger version is inferred from their numbers.
- Failure causes are read from error text (`lib/classify_failures.py`); the per-file first error is in the
  TSV for checking.
- The ledger statement digest's read time was not stamped by its query; it is bounded by the file's save
  time.
- Collision odds of the comparison tokens: 48-bit identities (~1e-8 over ~2,000 objects) and 24-bit
  content digests (~6e-8 per compared pair).
